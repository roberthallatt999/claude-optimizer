# Profile overrides

These win wherever the upstream rules below disagree. The values come from the active
ai-config profile, so the same skill serves work, volunteer and side projects.

0. **Read the profile first.** Run `~/.claude/skills/noslop/scripts/profile.sh` from the
   project folder. It prints `key=value` lines: `name`, `organization`, `voice`, `spelling`,
   `share_domain`, `sensitive`, `not_for`. If it prints `profile=none`, ask the user who the
   page is from and where (if anywhere) to publish it, then go on with those answers. Below,
   ⟨key⟩ means that profile value.
1. **Who it's from.** The header line reads "From ⟨name⟩, ⟨organization⟩ to …" (just
   "From ⟨name⟩ to …" when organization is empty). With `voice=first-person-singular`, write
   as "I", never "we", "our team" or "the team"; with `first-person-plural`, "we" is fine.
2. **What it's for.** Standalone pages for a reader. Not ⟨not_for⟩: site code follows the
   project's own brand and stack rules, not this skill.
3. **Accessibility (WCAG AA).** Two upstream style-kit colours fail 4.5:1 for text, so
   override them:
   - `--text-3: rgba(0,0,0,.55)` in light mode and `rgba(255,255,255,.5)` in dark mode.
   - `--clay-strong: #b5502f`, so white text on the main button passes.
   - Clay (`#d97757`) is for bars, borders and accents only, never text on white.
   - Every coloured status carries a word as well ("Late", "On track"), never colour alone.
   - Tabs, steps, Back/Next and opening rows work from the keyboard with a visible focus ring.
4. **Every page goes to ⟨share_domain⟩ by default** when the profile sets one. Whatever the
   request calls it (a page, a report, an update, a dashboard, a mock-up) and whether or not it
   says "link", publish it with the steps in rule 5. This replaces the upstream rule "Always
   build a plain HTML artifact". Build plain HTML into `dist/index.html`. Use section 8's React
   stack only when the user asks for a website or the web version.
   - With no share_domain, build `dist/index.html` locally and publish nothing until asked.
   - Make a Claude artifact instead only when the user asks for an artifact.
   - If the page would hold personal information about ⟨sensitive⟩, stop before building and
     ask the user how to protect it. A shared passcode can't say who opened the page, so it
     isn't enough; neither is a Claude artifact. Never publish such a page as a Claude artifact.
   - When the Artifact tool does publish, its page contract (allowed CDNs, dark-mode token
     guards, size limit) still holds. Every design decision comes from this skill.
5. **Publishing to ⟨share_domain⟩, through Cloudflare (not GitHub and Vercel).** These steps
   replace section 8's "Private by default" steps. Section 8's stack, motion and checking rules
   apply when building the React version. The helper is
   `~/.claude/skills/noslop/scripts/cloudflare.sh`; it takes its share domain from the profile.
   1. Run `cloudflare.sh config`. If the token is missing, ask the user to run
      `! ~/.claude/skills/noslop/scripts/cloudflare.sh setup`, then run `cloudflare.sh check`.
      Never read the token any other way, and never print it.
   2. In a new folder for the page, run `cloudflare.sh new . "<topic>" [days]`. It names the
      page `<topic>-<random hash>`, checks with Cloudflare that the name is unused, sets it to
      expire in 30 days unless the user asks for another span, and prints the address
      `https://⟨share_domain⟩/<name>/`. Keep the topic short and free of personal names.
      To update a page, work in its folder: `new` keeps the existing name and address. Set
      `PAGE_TITLE` in `wrangler.jsonc` to the header line's "what this is".
   3. Build into `dist/` with relative asset links (Vite: `base: './'`), because the page is
      served under its path. A single HTML page goes in `dist/index.html`.
   4. Deploy with `cloudflare.sh wrangler deploy`. The safety hook asks the user first.
   5. Set the passcode with `cloudflare.sh passcode <name>`. It makes one of three plain words
      and two digits, sets it on the page and records it on this machine. Until it is set, the
      page answers "not ready" to everyone.
   6. Check from outside with curl: the address from `cloudflare.sh url <name>` must answer
      401, and a POST of the passcode to `<address>__unlock` must answer 303. A 403 page that
      says "Sorry, you have been blocked" is a Cloudflare security rule on the zone, not the
      gate: tell the user and leave the rule alone.
   7. End with 3 lines: the link, the passcode, and the expiry date. After that date the page
      answers "expired" by itself.

   Managing pages: `cloudflare.sh describe <name>` shows a page's address, title, dates, source
   folder and recorded passcode. Cloudflare can't return a passcode, so when none is recorded,
   `cloudflare.sh passcode <name>` sets a new one. `cloudflare.sh list` shows every page on
   the share domain with its dates.
   `cloudflare.sh prune` lists the expired ones, and `prune --delete` removes them.
   `cloudflare.sh delete <name>` removes one page early. Both deletes need the user's yes, and
   neither touches a Worker that isn't served from the share domain.

   Don't create a GitHub repo or push unless the user asks. Cloudflare may serve from outside
   the user's country and the passcode is light protection: one shared code, no record of who
   viewed the page, no limit on guesses. Never put personal information about ⟨sensitive⟩
   behind the passcode alone.
6. **Polish tools are opt-in, per page.** Emil Kowalski's skills, Impeccable and Magic UI
   are not installed by default. Offer them once when building the web version. Install them
   only in that page's folder and only on the user's yes, never globally.
7. **Language.** Write in the language of the source material. English prose uses ⟨spelling⟩
   spelling (Canadian: colour, centre, paediatric).
